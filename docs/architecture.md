# Runlet architecture

Recorded 2026-10-02. This file describes the code in this repository on that date. `plan.md` asks for package versions, the deployment target, and module boundaries to be recorded here.

- The execution, persistence, and language-service layers (`Packages/RunletKit`) are implemented and covered by 458 package tests.
- The native app target (`Runlet/`) is implemented. XCUITests in `RunletUITests/` drive the rendered app, and `scripts/package.sh` builds, verifies, and self-tests an installable universal app.
- Measurements, prototype-gate results, and Laravel completion coverage are in [compatibility.md](compatibility.md).
- Requirement-to-evidence status is in [validation.md](validation.md).

## Repository layout

```text
project.yml                  XcodeGen spec: Runlet app, RunletUITests, Runlet scheme
Runlet/                      macOS app target (SwiftUI + AppKit)
  App/                       RunletMain (+ --self-test), AppModel, TabModel, SelfTest, AppResources
  Editor/                    AppKit code editor, PHPantom binding, SwiftUI wrapper
  Features/                  SwiftUI views: window, tabs, targets, output, sheets, settings, library
  AppIcon.icon/              app icon for Icon Composer (Liquid Glass), from scripts/app-icon/
  Assets.xcassets/           classic AppIcon.appiconset (fallback), from scripts/app-icon/
RunletCLI/                   the `runlet` command-line tool and `runlet mcp` (copied into Contents/Helpers)
RunletUITests/               XCUITests driving the built app
Packages/RunletKit/          Swift package: RunletCore, RunletExecution, RunletLanguage + tests
Resources/Runner/            PHP runner: src/ (Runner.php, Drivers.php, Inspector.php, Benchmark.php, Profiler.php), build deps (composer.json, build/vendor),
                             generated bundle dist/runlet-runner.php
Resources/Sandbox/laravel/   pinned Laravel sandbox template and runlet-sandbox.json
Resources/LSP/               PHPantom universal binary (fetched) and its license
Resources/Licenses/          license notices of bundled third-party code (SwiftTerm)
Tests/Fixtures/              disposable plain, Composer, Laravel, LSP, and Docker fixtures,
                             plus fake-docker/ (a fake Docker CLI for screenshot tours)
scripts/                     build, fetch, embed, fixture, packaging, and app icon scripts
docs/                        architecture, compatibility, validation
build/                       generated: DerivedData, UI test logs and result bundles
dist/                        generated by scripts/package.sh: Runlet.app, .zip, .dmg, self-test.json
```

The plan's suggested layout used three separate packages. This repository uses one package, `Packages/RunletKit`, with three library targets instead.

## Module boundaries

```text
Runlet (app) ──► RunletCore, RunletExecution, RunletLanguage, SwiftTerm, RunletCLI (embedded tool)
RunletCLI (runlet) ──► RunletCore
RunletExecution ──► RunletCore
RunletLanguage  ──► RunletCore
```

`RunletExecution` and `RunletLanguage` do not depend on each other, so PHP execution and language intelligence stay independent. Package targets import only `Foundation` and `Darwin`. AppKit, SwiftUI, and Observation are used only in the app target.

## Runner and transport

**Build.** The runner source is `Resources/Runner/src/`, written with PHP 7.4-compatible syntax: `Inspector.php` (the run inspector and its database hooks), `Drivers.php` (the driver API and built-in drivers), `Benchmark.php` (`Runlet\bench()` and `Runlet\Benchmark`), `Profiler.php` (Profile Run's Excimer sampling), `Runner.php`, `SqlTab.php` (SQL tabs' statement runner, #35), `SqlConnect.php` (saved database connections, #138), `SqlSchema.php` (their catalog reader for completion and the schema explorer, #128, #21), `SqlExplain.php` (Explain Statement's dialects and Explain Analyze's guards, #147; `Runlet\explainPlan()`, which the inspector's Explain tab calls, #170), `SqlDefinition.php` (Show Definition's catalog reads and PostgreSQL reconstruction, #148), `SqlCancel.php` (Stop's server cancel, #144), `SqlServerInfo.php` (the Database pane's Server section: server details, sizes, sessions, Cancel Query and Kill Session, #150), `MagicComments.php` (the magic comments' probe planner and the `Probe` runtime), and `Panels.php` (App Info's built-in sections, bounds, and redaction, #19). `scripts/build-runner.php` writes a single file, `Resources/Runner/dist/runlet-runner.php`, that contains:

- The runner, in that order.
- nikic/php-parser 5.9.0, with its namespace rewritten from `PhpParser\` to `RunletVendor\PhpParser\`. Builders, pretty printers, and other unused parts are left out.

The scoped parser never collides with a project's own php-parser. Edit `src/`, never `dist/`.

**Per-run script.** `RunnerBundle.script` appends `namespace { \RunletRunner\Runner::main('<base64 JSON>'); }` to the bundle. The request carries:

- `protocolVersion` and `runId`
- `nonce`
- `mode`: `"run"` (default) runs `code`; `"commands"` boots the project the same way and lists its commands instead (see [Project commands](drivers.md#project-commands)); `"panels"` boots it and reports its App Info sections (see [App Info](drivers.md#app-info))
- `code`
- `bootstrap` (`"auto"`)
- `strictTypes: true`, only when the run declares strict types
- `magicComments: false`, only when magic comments are turned off in Settings: the runner then leaves them alone (no probes, no `probes` event)
- `inspector` (runs only): `enabled`, `interceptMail`, `previews`. Without it the runner records nothing (except benchmarks and profiles, which the run asked for).
- `profile` (Profile Run only): `engine` (`excimer`), `periodMs` (1), `eventType` (`wall`, or `cpu` on Linux and BSD)
- limits: `maxDepth`, `maxChildren`, `maxStringBytes`, `maxNodes`, `maxValueBytes`, for magic comments `maxInlineHits` (100) and `maxInlineBytes` (16 MiB), and for the inspector `maxQueries` (2,000), `maxRecords` (2,000 other records), `maxRecordBytes` (8 MiB for all records), and `maxBodyBytes` (2 MiB per HTML or text body)

**Transport.** The whole program is streamed to `php` on stdin, with the arguments `-d display_errors=stderr -d html_errors=0 -d log_errors=0`. Nothing is written into the project or the container, so read-only filesystems and non-root users work. The request at the end of the program (base64 JSON) is the only place a saved connection's password travels (`sqlConnection`, #138): never in arguments, environment variables, files, or the Run Log, which logs the script's size. The plan's first candidate was a per-run event file. It was not used, but the event contract is unchanged.

**Event framing.** Events are framed records on stdout:

```text
0x1E "RL1:" <nonce> ":" <decimal byte length> ":" <json> "\n"
```

- The nonce is 16 random bytes in hex, generated per run with `SecRandomCopyBytes`.
- All other stdout and stderr bytes are the application's raw output.
- `FrameDecoder` handles frames and markers split at any byte. It holds back a possible partial marker at the end of a chunk.
- Frames with another nonce stay raw output.
- A truncated or malformed frame becomes a `transport` error.

**Runner frame types.**

- `started`: pid, PHP version and binary, SAPI, working directory, framework, euid, and `profilers` (`{excimer?, spx?}` versions of the loaded profiler extensions)
- `bootstrapped`: framework, framework version, `bootstrapMs`, and the application's `environment` when the driver reports one
- `dump`, with an optional `preview` (below)
- `result`: `hasValue`, `value`, and an optional `preview`: `{kind, title, subject?, html, text?, htmlOmittedBytes?, error?}`, the driver's `preview()` of a returned or dumped object (mailables, mail notifications, views, `Htmlable`/`Renderable`, HTML Symfony responses), only when `inspector.previews` is on. A failing render sends `error` instead of `html`.
- `error`. An `exit()` during bootstrap gets a hint: the driver's `bootstrapExitHint()` (WordPress: the redirect it tried, its status, and the file and line that sent it, with advice for `install.php` and HTTPS redirects), then the project file loaded last.
- `notice`: `{message}`, Runlet's own notice. With `level` (`notice`, `warning`, `error`) and `user: true` it is a card from `\Runlet\notice()`, `warning()`, or `error()` (#196), with the caller's `inSnippet`/`snippetLine` or `file`/`line`, and optional `context` (a value node), `omittedBytes`, and `exception` (`className`, where it was thrown, `trace`, `previous`). `SnippetMessage.noticeEvent(payload:)` decodes a leveled one as `RunEvent.Kind.snippetMessage`, which never sets the run's error state. `SnippetMessages.php` bounds them (16 KB per message, 200 cards and 8 MB per run, then one plain notice with the count).
- `log`: `{source, message, detail?}`, a Run Log line (Run ▸ Show Run Log): the driver chosen and why, the boot time and variables, a WordPress request's host and redirects, `exit()` during bootstrap with the last files loaded, and driver lines from `Driver::log()`. The app adds its own lines: `launch` (the executable and arguments as one shell line, the working directory, and the runner script's size on stdin; never environment values), `runner` (started: PHP, binary, pid, uid), `stderr`, `error`, and `exit` (status, reason, exit code, elapsed). `TabModel.runLog` keeps up to 500 lines per run.
- `remember`: `{key, value}`, a value the app keeps for this target until it quits and sends back as the request's `hints` (`driver` = `builtin:<key>@<.runlet stamp>`; `wordpress.siteUrl` = `<wp-config.php mtime:size> <url>`). The runner checks each hint is still valid before using it, and the app drops a target's hints when a run fails while booting.
- `inspector` (runs with the inspector on, after `bootstrapped`): `sections` the driver shows even when empty, `interceptMail` (asked for), `interceptingMail` (a driver confirmed it), `driverName`, `interceptMailReason?` (why the driver can't intercept, #192)
- `record`: `{index, section, kind, title?, inSnippet?, snippetLine?, file?, line?, data}`. `kind` is `query` (`sql`, `bindings` as `{type, value?, name?, size?, omittedBytes?}`, `timeMs?`, `connection?`, `driver?`, `rawSql?`, `omittedBindings?`, `omittedBytes?`), `mail` (`subject`, `from`/`to`/`cc`/`bcc`/`replyTo` as `{address, name?}`, `html?`, `text?`, `attachments`, `mailer?`, `mailable?`, `caller?`, `intercepted`, `error?`, `queued?`, `queueConnection?`), `log` (`level`, `message`, `channel?`, `context?` value), `html` (`html`), `value` (`value`), `benchmark` (`source`, `method`, `results` of `{label, iterations, requestedIterations, warmup, stoppedBy, firstNs, totalNs, minNs, maxNs, meanNs, medianNs, p95Ns, p99Ns, stddevNs, opsPerSec, memory{peakBytes, perCallBytes, firstCallBytes}, histogram{lowNs, highNs, binNs, counts, above}, series, averageOnly?}`, `budgetMs`, `overheadNs`, `notes`), or `profile` (`engine`, `version`, `eventType`, `periodMs`, `samples`, `durationMs`, `outsideSamples`, `maxStacks`, `maxDepth`, `collapsed`, `frames` of name → `{line, file?, inSnippet?}`, `truncated{stacks?, foldedSamples?, deepSamples?}`). Unknown kinds decode as `unknown` so newer runners stay readable.
- `recordLimit`: `{section, omitted, reason}` (`count` or `bytes`), sent when the run finishes, for records the limits left out
- `commands` (commands mode only): `origin` (`composer` or `driver`), `source`, `commands` of `{name, command, description, group}`; the driver event also has `framework` and, for project drivers, `driverFile`
- `panels` (panels mode only): `origin` (`builtin`, then `driver`), `source`, `sections` of `{title, rows: [{key, value, redacted?}], omittedRows?}` (values are strings, numbers, booleans, null, or lists of strings, already bounded and redacted), `redacted`, and optional `omittedSections`, `notes`, `error` (a failing built-in or `panels()`), and `driverFile`
- `probes` (runs with magic comments, before the snippet runs): `probes` of `{id, line, kind, comment}` (`kind` is `value`, `time`, or `reached`) and `rejected` of `{line, comment, reason, label}`
- `inline`: `{probe, line, kind, hit, t, value?, ms?, error?, sampled?, final?, omitted?}`, one per hit while the snippet runs (see [Magic comments](#magic-comments-10))
- `runnerFinished`: reason, `elapsedMs`, `peakMemory`, `executeMs`

`RunSession` turns `runnerFinished` into the backend's `finished` event.

**Run inspector.** Runs create one `Runlet\Inspector` before bootstrap (so `WordPressDriver` can turn on `SAVEQUERIES`), then call the driver's `inspect()` after `bootstrapped` and before the snippet compiles; a throwing hook becomes a notice. Records carry the snippet line from the backtrace: frames of `eval()`'d code count as the snippet only when evaluated on `Runner::evaluate`'s line, so other evaluated code (the DBAL 4 middleware) never claims a snippet line. Callbacks registered with `atFinish()` (the Eloquent query-log fallback) run in `finish()`, before `recordLimit` and `runnerFinished`. The drivers' hooks and the API are documented in [drivers.md](drivers.md#run-inspector).

**Bootstrap.** Framework detection in `auto` mode:

- `laravel` if `artisan` and `bootstrap/app.php` exist.
- `composer` if `composer.json` or `vendor/autoload.php` exists.
- `plain` otherwise.

Composer and Laravel projects require `vendor/autoload.php`. If it is missing, the runner reports a bootstrap error that tells the user to run `composer install`. For Laravel, the runner requires `bootstrap/app.php`, resolves the console kernel, calls `bootstrap()`, and reports `$app->version()`. Plain directories run without an autoloader, and relative includes resolve against the working directory.

**Snippet compilation** (`SnippetCompiler`):

1. If the code does not start with `<?php` or `<?=` (after whitespace), the runner prepends `<?php ` on the same line, so line numbers do not change. Column numbers for parse errors on line 1 are corrected for the prefix length.
   With `strictTypes`, and unless the code has its own `declare(strict_types=…)` (found with the tokenizer), `declare(strict_types=1);` is inserted right after the opening tag on the same line, after the other steps, so lines and parse-error columns are unchanged. Whitespace before a snippet's own `<?php` moves after the declaration; a leading `<?=` gets `<?php declare(strict_types=1); ?>` in front.
2. The code is parsed with `ParserFactory::createForHostVersion()`. If parsing fails, the runner retries with `"\n;"` appended, which accepts an omitted final semicolon. If that also fails, it reports a `parse` error with the snippet line and column.
3. The runner finds the last top-level statement, looking inside a trailing namespace and skipping trailing comments (php-parser's `Nop` statements, so `1 + 1; // note` still has a result). A final expression statement (other than `exit`) becomes `return <expr>;` (`return ` is inserted before it and the rest of the statement becomes `;`). A final `return` is kept.
4. A sentinel `return \RunletRunner\NoResult::instance();` is appended. It goes inside a trailing braced namespace if there is one, and PHP mode is reopened if the source ends in inline HTML. In the result, `NoResult` means "no implicit result", which is distinct from `null`.
5. Magic comments become probe calls inserted at byte offsets (see [Magic comments](#magic-comments-10)). All edits are insertions or replacements applied back to front; edits at one offset are joined in a fixed order (closing parts, replacements, inserted statements, `return `, opening calls from the outermost in).
6. Without the tokenizer extension, no implicit result is captured and the runner emits a `notice`.

**Evaluation.** `eval()` runs inside the private static method `Runner::evaluate`, so snippet variables live in their own function scope and never touch runner state. Every run is a new PHP process, so no state carries over between runs.

**Dumps** (`installDumpHandler`):

- `VarDumper::setHandler` is installed on `Symfony\Component\VarDumper\VarDumper` and on any VarDumper class referenced by the files that define the active `dump()`/`dd()`.
- The search follows php-scoper-style aliases up to depth 3, which covers tools loaded with `auto_prepend_file` such as global Ray.
- If no VarDumper and no `dump`/`dd` functions exist, the runner defines its own `dump()` and `dd()`.
- A `dd` call is detected from the backtrace. It is marked `origin: "dd"`, and the run finishes with reason `dd`.

**Values** (`ValueNormalizer`):

- No getters, `__toString`, `__debugInfo`, `__get`, or JSON serialization are invoked.
- Limits: depth 8, 200 children, 64 KiB per string, 20,000 nodes, and 2 MiB per value.
- Objects get reference IDs, and an object seen again is marked `repeated`. Array references are marked `recursion`.
- `var_dump` and `print_r` stay plain text on stdout.

**Errors.** Throwables become `error` events with:

- stage, class, and message (eval paths are rewritten to "snippet")
- `snippetLine` or file and line
- a trace of up to 40 frames, with runner frames removed
- the previous exception

A shutdown function reports fatal errors as `FatalError` with `fatal: true` and reason `fatal`. `exit` and `die` finish with reason `exit`.

## Profile Run

Run ▸ Profile Run (⌥⌘R, and in the Command Palette; [#41](https://github.com/filipac/runlet/issues/41)) runs the tab like Run, through the same production confirmation and the same target resolution, with `request.profile` set.

- **Detection.** Every run's `started` frame lists the PHP's profiler extensions, and so do PHP discovery (the sandbox's and local projects' PHP, with their php.ini), the Docker profile's Test, and SSH Test Connection (`PHPProfilers`). The app keeps them per target (`TargetFacts.profilers`). Settings ▸ PHP shows a badge per installation, and both probes show a Profilers row.
- **Availability.** `ProfileRunAvailability`: enabled when the target's PHP loads Excimer, or when nothing is known yet (a container or server not run or probed since); disabled with the reason otherwise ("Profile Run needs the Excimer extension, which PHP 8.4.25 (Herd) doesn't load."). The Command Palette lists the disabled command with its reason; the Run menu item shows it as its tooltip.
- **In the runner.** Without Excimer, the runner reports `ProfilerUnavailable` right after `started` and stops before the project boots, so nothing runs. Otherwise `Profiler` starts an `ExcimerProfiler` (wall time, 1 ms period) just before `Runner::evaluate()` and stops it when the snippet returns, throws, or exits; the application's bootstrap is not profiled. A flush callback every 2,000 log entries keeps memory bounded. Each sample's trace is cut at `Runner::evaluate()`, so the runner's frames never show; the snippet's top level becomes `snippet:<line>`, closures `{closure:<file or snippet>:<line>}`, methods `Class::method`, included files their path. The record keeps the 4,000 most sampled stacks (the rest fold into `[other stacks]`), at most 200 frames deep (`[deeper frames]`), and at most 2 MiB of collapsed text, plus each frame's file and most sampled line. It is sent from `finish()`, before the inspector finishes, so completed, failed, `exit`, and fatal runs all report it.
- **SPX** is detected and named, but not used: it profiles only processes started with `SPX_ENABLED=1` (an environment variable read when PHP starts) and writes its reports to files in `spx.data_dir` or to stderr, with no API that returns them to the script ([php-spx README](https://github.com/NoiseByNorthwest/php-spx)).
- **In the app.** The `profile` record adds a line to the output and selects the Profile section (unless the run failed). `FlameGraph` builds the tree off the main thread; `FlameGraphCanvas` draws it.

## Applying events (#82)

`AppModel.startRun` reads a run's events through a `RunEventFeed` and applies them to the tab in batches, paced by `OutputPacer`: the first batch at once, then at most every 100 ms, and while the output is slow to lay out and draw, three times as long as the main thread stayed busy (up to 1 s). A run that prints thousands of lines or dumps therefore updates the tab a few times a second, and the UI keeps most of the main thread. `finished` is applied as soon as it arrives. The run's observer (an MCP client's run report, [#43](https://github.com/filipac/runlet/issues/43)), the session hints, and what Runlet learns about the target get every event, in order, whatever the Output setting.

**Output: Realtime or At once** (Settings ▸ General ▸ Output, `AppSettings.outputDelivery`, Realtime by default; read when Run is pressed, for the whole run). `TabModel.apply` passes each event through the run's `RunEventGate`. In At once mode the gate holds the output (printed output, dumps, the result, errors, notices, inspector records, magic-comment values) and releases it, in arrival order, with `finished`, so a run that completes, fails, calls `dd()` or `exit`, is stopped, or loses its process or SSH connection shows everything that arrived (the engine always ends a run with `finished`). The status (running, elapsed time, Stop) and the Run Log stay live. Holding happens in the app, as #10 did for magic-comment values, so every target behaves the same and the PHP process holds nothing. Clear Output during a run drops what was held, as it drops what was shown in Realtime. Settings files from before #82 decode with Realtime, or At once when they had #10's *Show values while the code runs* turned off (`streamInlineValues: false`); that key is no longer saved.

**Large output.** Measured before #82 with a Debug build (local PHP 8.4 and the SSH fixture), the output fell minutes behind a run and froze the window: 5,000 `dump()` calls had 3,400 cards after 90 s, 200,000 echoed lines (2.3 MB) had 29 KB after 60 s, and output near the 8 MiB limit had 195 KB after 60 s, with the main thread busy the whole time. The causes were one SwiftUI update per event, a printed-output card laid out again in full for every chunk (one `Text` holding all of it), and scrolling to the last card after each one, which places every card above it. Now: events are batched and paced as above; printed output is a `ChunkedText` whose pieces are separate lazy rows; the Structured view shows the last 5,000 lines of a printed output and the last 1,000 cards (Show All lifts that; Plain, Raw, Copy and Save Output always have everything); and Plain and Raw are a native text view that appends. The same runs now finish in the tab within a few hundred milliseconds of the process (the PR for #82 has the numbers).

## Magic comments (#10)

`//?`, `/*?*/`, `/*?->projection*/`, and `/*?.*/` show values in the editor while the code runs. [compatibility.md](compatibility.md#magic-comments-10) lists what each form shows and the placements Runlet refuses.

**Compiler** (`MagicComments`, called by `SnippetCompiler` only when the code contains `//?` or `/*?`):

- `token_get_all` finds `T_COMMENT` tokens of the four forms, so text in strings, heredocs, other comments, doc comments, and inline HTML never counts. Each comment is resolved against the token before it (whitespace and comments skipped): (1) an expression ending there, the outermost first, looking inside parentheses, and inside an arrow function's body, `yield`, `print`, or `throw`; (2) for `//?` and projections, a statement ending there on the same line (expression statements, `return`, `echo`; `$i++;` shows `$i` afterwards); (3) for `//?` and `/*?.*/`, a statement position between statements (in a statement list region found from the braces or alternative-syntax colons), where `Probe::hit(id);` or `Probe::mark(id);` is inserted (before a `return`, `break`, `continue`, `throw`, or `exit` that ends right before the comment; around the final expression when it becomes the result).
- A walk over the php-parser tree records each expression's context: read, written, taken by reference, checked by `isset`/`empty`/`??`, a constant expression, the start of a `{$…}` interpolation, a slot that can't hold a call, or a call argument. An argument's by-reference-ness comes from the callee: functions and classes the snippet declares (`use` imports and namespaces resolved by hand), and loaded functions and classes through reflection (classes are never autoloaded for this); methods on objects are unknown. Read contexts get `\RunletRunner\Probe::at(id, <expr>)`; by-reference ones whose expression is a variable, element, or property get `Probe::ref(…)` (a by-reference parameter and return, so `=&`, `foreach (… as &$v)`, by-reference returns and yields, and by-reference arguments keep their references); projections get `Probe::tap(id, <expr>, fn ($__runletProbe) => $__runletProbe<chain>)`, timings `Probe::time(id, <expr>)`. A wrap that would end a nullsafe chain's short-circuit (a `?->` chain followed by `->`) is refused. Everything else is refused with a reason and a short label.
- Nothing is pretty-printed. Inserted text has no line breaks (a projection is re-tokenized onto one line without comments), and the instrumented source must parse with the same parser and keep its line count; otherwise every probe is dropped with a notice and the snippet runs as written.

**Runtime** (`Probe`, armed by `Runner` with the compiled probes after the `probes` event; `begin()` right before `eval`):

- Each hit counts. The first `maxInlineHits` (100) hits of a probe are sent with a value (a `ValueNormalizer` limited to depth 5, 100 children, 8 KiB strings, 2,500 nodes, 256 KiB); later hits are sent about every 250 ms with `sampled`, and `finish()` (from `Runner::finish`, before `runnerFinished`) sends `final` counts for probes whose last hit wasn't sent. After `maxInlineBytes` of values, hits are sent without values (`omitted: bytes`).
- A projection runs only for hits whose values are sent; one that throws is reported as `error` and the value passes on. `/*?.*/` measures from the previous mark of the run (any `/*?.*/`), or from `begin()`. Probe methods never throw and call no user code besides projections.
- Events go through `Channel` like every other frame, so they stream on every transport.

**Settings** (General ▸ Magic Comments, `AppSettings.magicComments`, on by default; read when Run is pressed, for the whole run):

- *Show values of magic comments* off: `RunRequest.magicComments` is false, so `RunnerBundle.script` sends `magicComments: false` and `SnippetCompiler` skips `MagicComments` entirely. There is one script per run for every adapter, so no target gets probes. The editor stops highlighting them (they color as ordinary comments) and shows no values or gutter marks, also for events of a run that was already going. Profile Run always sends `magicComments: false`, so its flame graph shows only the code as written.
- When values appear follows Settings ▸ General ▸ Output ([#82](https://github.com/filipac/runlet/issues/82), see [Applying events](#applying-events-82)), which replaced #10's *Show values while the code runs* switch: At once holds inline events with the rest of the output. Holding them in the app rather than batching in the runner keeps one code path for every target, keeps the values already received when a run is stopped (SIGKILL), crashes, or loses its connection, and costs the PHP process no memory. Runner-side batching would save little: each value has to be captured when its line runs anyway (objects change later), so only the small per-hit frame writes would move to the end.

**Editor**: `TabModel` passes `.inline` events to the tab's `InlineValueOverlay` with `RunRequest.editorLine(forSnippetLine:)`, so Run Selection maps back to the selected lines. Values are drawn only for visible lines, and the hover panel and the gutter markers read the same `InlineValues`. The next run clears them; edited lines lose theirs. Values never start a run.

## Run lifecycle (`ExecutionEngine`)

1. **Snapshot.** A `RunRequest` captures:
   - the tab ID and document version
   - the code, which is only the selection for Run Selection, with the selection's start position
   - a `TargetSnapshot` with the resolved working directory, PHP executable, container ID, user, and profile revision

   Later edits or target changes cannot redirect an active run.
2. **Admission.** Each tab can have one active run. A second `start` for the same tab throws `ExecutionError.tabBusy`. Docker targets require a located Docker CLI.
3. **Bounded concurrency.** Runs in different tabs execute concurrently, up to `maxConcurrentRuns` (default 4). Further runs wait for a free slot.
4. **Launch.** The adapter builds a `ProcessSpec`: an executable path plus an argument array, with no shell. `SupervisedProcess` then:
   - starts the child with `posix_spawn` in a new process group, with default signal dispositions
   - writes stdin on a background thread, with `SIGPIPE` suppressed
   - reads stdout and stderr on dedicated threads
   - reaps the child on its own thread

   `RUNLET_RUN_ID` is set in the runner's environment for every adapter.
5. **Event pump.** `RunSession` decodes frames and numbers events 1…n. Byte order is preserved within each raw stream, but interleaving between stdout and stderr is not guaranteed.
6. **Output limit.** Up to `RunLimits.maxRawOutputBytes` (8 MiB) of raw stdout plus stderr is kept per run. Further output is still read and discarded, so a full pipe cannot deadlock the process, and `finished.truncation` reports the discarded byte count. How the app applies the events is in [Applying events](#applying-events-82).
7. **Exactly one `finished`.** It is always the last event:

| Situation | `status` | `reason` |
| --- | --- | --- |
| Snippet completed | completed | `completed` |
| `dd()` | completed | `dd` |
| `exit`/`die` | completed if exit code 0, else failed | `exit` |
| Parse, bootstrap, or execute error | failed | `error` |
| PHP fatal error | failed | `fatal` |
| Stop after launch | cancelled | `cancelled`, or `cancelled: <note>` when the stop could not be confirmed |
| PHP or directory missing, container gone or not running, spawn failure, or process exited before the runner started | failed | `launch-failed` (with a `launch` error) |
| Process ended without `runnerFinished` | failed | `transport-closed` (with a `transport` error) |
| Stop before the process launched | cancelled | `cancelled` (`cancel` reports "Stopped before the PHP process launched.") |

For Run Selection, the selection's start line is added to runner line numbers to map them back to the editor. On the selection's first line, the selection's start column is added too (`RunRequest.editorColumn(forSnippetLine:column:)`); later lines keep their columns.

## Cancellation (Stop)

`ExecutionEngine.cancel(runId:)` marks the run as cancelled, then calls the adapter's stop operation. An SQL tab's run that reported its database session first has its statement [cancelled on the server](#cancelling-an-sql-statement-on-the-server-144) (#144). It returns a `CancelOutcome`, where `confirmed` is true only when Runlet saw the PHP process end.

| Adapter | Mechanism |
| --- | --- |
| Local (`LocalAdapter`) | The runner leads its own process group. Stop sends `SIGTERM` to the group, waits 1.5 s, sends `SIGKILL` to the group, and gives up after 5 s in total. Child processes started by the snippet are in the same group and stop too. |
| Existing container (`DockerExecAdapter`) | See below. |
| Docker sandbox (`DockerSandboxAdapter`) | The run uses `docker run --rm -i --init --name runlet-sandbox-<first 8 of runId> --label dev.runlet.owned=sandbox`. `--init` makes a small init PID 1 that forwards signals, so PHP is never PID 1 (which would ignore `SIGTERM`). Because Runlet owns that container, Stop kills the whole container, including any children of the snippet. Stop can arrive before `docker run` has created the container, so `docker kill` is retried every 100 ms until it succeeds or the client exits, for up to 4 s. Runlet then waits up to 4 s for the client. If that fails, it runs `docker rm -f`, waits 2 s, and finally terminates the local client and reports the stop as unconfirmed. |

For an existing container, Stop works as follows:

1. Wait up to 2 s for the runner PID from the `started` event.
2. Run a separate `docker exec [--user U] <container> <php> -r <helper> -- <pid> <runId> <signal>`.
3. The helper reads `/proc/<pid>/stat` and treats a missing or zombie process as gone.
4. The helper requires `RUNLET_RUN_ID=<runId>` in `/proc/<pid>/environ`. On a mismatch it does not send a signal.
5. The helper signals with `posix_kill`, falls back to `exec('kill …')`, and otherwise reports `unsupported`.
6. The sequence is `SIGTERM`, a 1.5 s wait, `SIGKILL`, a 3 s wait, then a signal-0 check.

Runlet never uses `docker stop` or `pkill`, so the application container keeps running.

For an SSH host (`SSHExecAdapter`), Stop runs `RemoteSignal.wholeRunHelper` over a second SSH session through the shared connection. It signals the runner and every process whose `/proc/<pid>/environ` carries the run's `RUNLET_RUN_ID` (what the snippet started, even after `setsid`), with the same SIGTERM, 1.5 s, SIGKILL, 3 s, check sequence. Killing the local `ssh` alone would not stop PHP: without a pty the remote side gets no SIGHUP, and a shared connection keeps the session open. Hosts without `/proc` are not signalled, and the stop is reported as unconfirmed.

Known limitations, also listed in [compatibility.md](compatibility.md):

- Docker Stop signals only the runner PID, so processes a snippet spawns inside a container may survive.
- In-container Stop needs Linux `/proc`, plus either `posix_kill` or `/bin/sh` with `exec()`. Without them the outcome is reported as unconfirmed.

### Cancelling an SQL statement on the server (#144)

Stopping the runner doesn't stop the database. MySQL and MariaDB keep executing a long statement until they write to the closed connection, and PostgreSQL usually finishes it (unless `client_connection_check_interval` is set). Locks stay held meanwhile. So an SQL tab's run (Run, Run All, Load Next, Explain) cancels its statement on the server before the adapter's stop:

1. **The session.** Right after the runner resolves the connection, and before the statement runs, `SqlCancel::report()` (`Resources/Runner/src/SqlCancel.php`) emits an `sqlSession` event: the PDO driver, the server-side id (`CONNECTION_ID()`, `pg_backend_pid()`, `@@SPID`), the tab's application connection name (none for a saved connection), whether Run All runs in a transaction, and a 16-character hash of what identifies the server (MySQL's `@@hostname` and `@@port`, PostgreSQL's `pg_postmaster_start_time()` and `inet_server_port()`, SQL Server's `@@SERVERNAME`). It never carries credentials. SQLite and callable connections (`$wpdb`, Doctrine without PDO, a driver's callable) report none. `RunSession` keeps it in `RunControl.sqlSession` and adds a Run Log line ("Database session 4711 (mysql): Stop cancels its statement with KILL QUERY 4711").
2. **The plan.** `SQLCancel.plan(for:)` (RunletCore) gives the dialect's statement: `KILL QUERY <id>` (MySQL, MariaDB), `SELECT pg_cancel_backend(<pid>)` (PostgreSQL), `KILL <spid>` (SQL Server, which ends the whole session; untested live). Other drivers have none.
3. **The second runner.** On the first `cancel(runId:)` of a run with a session and a plan, `ExecutionEngine.cancelOnServer` (`SQLServerCancel.swift`) holds the run's `finished` event (`RunControl.holdFinish`), logs "Stop: cancelling the statement on the server with …", and launches a second runner with `SQLCancel.code`: on the target the run launched on (`ActiveRun.target`), with the run's request's saved connection (its password read from the `CredentialStore` again, on stdin) or hints (an application connection: the application boots again and opens the same connection through the same driver). It takes no run slot (`launch(…, usesSlot: false)`), so it never waits behind other runs. Docker targets get a second `docker exec` into the same container; SSH targets a second session over the shared connection. A saved connection that opens from this Mac (#142) ran with `LocalConnectionLaunch`'s local snapshot, so the second runner uses the same PHP in `<data>/LocalConnections` (and `LocalConnectionLaunch.check` refuses any other target). Its launch line goes to the run's Run Log ("Second runner: …").
4. **`SqlTab::cancel()`** resolves the connection like a run (no read-only refusal: the statement is Runlet's, and `KILL QUERY` and `pg_cancel_backend` on the user's own session work in a read-only session, #139) and calls `SqlCancel::cancel()`, which checks, in order: the connection is a PDO of the same dialect; the statement is exactly the dialect's own for the session; its own session isn't the target; the server fingerprint matches (a list of hosts, a load balancer, or a failover could reach another server, where the id is someone else's); the session (`information_schema.PROCESSLIST`, `pg_stat_activity`) exists, belongs to the same database user, and runs something. Then it sends the statement and watches the session for up to 1.5 s until the statement ends (PostgreSQL's `query_start` or MySQL's statement text and time change, or the session goes idle or away). It emits `sqlCancel`: `cancelled` (with `verified`), `stillRunning` (with the session's state, e.g. MySQL rolling back a large change), `alreadyEnded` (MySQL error 1094, `pg_cancel_backend` false), `idle`, `refused` (MySQL 1095, PostgreSQL 42501, SQL Server 6102, or one of the checks), or `failed`.
5. **The database's answer.** While the cancel runs (`RunControl.beginServerCancel`), `RunSession` holds an `error` frame that `SQLCancel.isCancellationError` reads as the dialect's cancellation error (MySQL/MariaDB 1317, PostgreSQL 57014 "due to user request"). When the server took the cancel (`cancelled`, `stillRunning`), the engine gives the runner up to 0.5 s to end on its own, then yields the held errors with `RunErrorInfo.interruptedByStop` (`settleServerCancel`); a later one is marked as it arrives. The output draws such an error as an info line (`SQLCancel.interruptedText`: "Interrupted by Stop.", with Run All's statement and rollback notes) instead of an `ErrorCard`; its `plainText` and the Run Log keep the database's message. A failed cancel releases the errors unmarked, and errors without Stop are never held.
6. **The report and the stop.** The engine yields `.sqlCancel(SQLCancelReport)` into the run (`interrupted` when an error was marked, so its message leaves Run All's rollback to that line; the output shows `report.message` as a notice, or a warning when it didn't succeed; the Run Log logs it; Load Next's card adds it to "Stopped."), releases `finished`, and then runs the adapter's stop as before. The whole step is bounded by `SQLCancel.timeout` (8 s): a second runner that doesn't answer is stopped and reported as `timedOut`. `CancelOutcome.server` carries the report.

Stop never asks, on production either: it only stops what already ran with confirmation. `cancelAll()` (quit) stops every run at the same time, each with its server cancel. If the runner is still alive when the database cancels the statement, the statement fails as for any error: Run All stops there and, in a transaction, rolls back. If the runner was already gone, the database rolls back the open transaction when it notices the closed connection.

Behind a transaction-pooling proxy (PgBouncer in transaction mode, ProxySQL), the reported id belongs to a pooled server connection that may serve another client by the time Stop cancels; the activity and user checks make that unlikely, not impossible. Session-pooling proxies and direct connections are not affected.

## Docker targets

- **CLI.** The Docker CLI is found through `ExecutableLocator`. `AppSettings.dockerExecutable` overrides it. The CLI uses the machine's selected Docker context.
- **Discovery.** Running containers are listed with `docker ps -q --no-trunc` and `docker inspect --type container`. Runlet-owned containers (label `dev.runlet.owned`) are excluded. A container can exit between `ps` and `inspect` (for example another application's container or one of Runlet's `--rm` sandbox containers). `docker inspect` then exits 1 but still prints the others, so Runlet accepts that exit when stderr only reports missing containers, and skips them.
- **Profiles.** `DockerProfile` stores:
  - a `ContainerIdentity`: Compose project and service labels, the container name as a fallback, and the last container ID and image
  - the working directory
  - the PHP executable (default `php`)
  - an optional user and the temporary directory (default `/tmp`)
  - an optional local source path and language PHP version
  - an optional strict-types override (nil follows the global setting)
  - `autoResolve` and a revision number

  `validate()` rejects relative paths, malformed users, and PHP values that start with `-`.
- **Resolution** (`DockerProfileResolver`):
  - With a Compose identity: one running match resolves, flagged as recreated if its ID changed. Several matches are ambiguous, and the user must choose. No match means not running.
  - Without Compose labels: the same container ID resolves. The same name with a new ID needs confirmation.
  - The resolver never picks a different container silently.
- **Launch.** The snapshotted container ID is inspected again right before launch. Runlet refuses to run if that container was removed or is not running. The command is `docker exec -i --env RUNLET_RUN_ID=<id> --workdir <dir> [--env TMPDIR=<tmp>] [--user <user>] <containerId> <php> -d …`. It uses no TTY and keeps the container's environment.
- **Probe.** `DockerCLI.probe` uses only `php -r` inside the container, so no shell utilities are needed. It reports:
  - PHP version and binary
  - user and uid
  - whether the working directory exists and is readable
  - framework
  - whether the temporary directory is writable
  - tokenizer availability
  - how Stop can signal (`posix`, `shell`, or `none`)
  - candidate application directories
- **Working-directory suggestions.** These come from the container's `WorkingDir`, its mount destinations, and common paths.
- **Temporary directory.** The profile's temporary directory is checked by the probe and passed as `TMPDIR`, so `sys_get_temp_dir()` and `tempnam()` work in read-only containers. Runlet itself writes nothing there.

- **Model.** Every target has an environment (development, staging, production) and an optional colour (`TargetLibrary.environment(for:)`, `color(for:)`, `isProduction(_:)`). The sandbox is always development.
- **Badges.** `EnvironmentBadge` next to the toolbar's target menu, on vertical tab cards (a PRODUCTION chip and a coloured stripe) and horizontal tabs, in the target menu (" — PRODUCTION"), ⌘P subtitles, and Settings ▸ Targets. Listing commands, running project or host commands, opening a shell or a REPL, and loading App Info always ask; confirming them never grants the grace. The Tests group doesn't ask on production: it is disabled there (`ProjectTests.isAllowed(on:)`), because test suites often reset or migrate the database; `runTests` refuses production targets too. The sheet is presented by the window whose tab asked.

- **The application's environment ([#12](https://github.com/filipac/runlet/issues/12)).** The runner calls the driver's `environment()` after `name()` and sends the cleaned name as `bootstrapped.environment` (`BootstrappedInfo.environment`; absent for plain and Composer projects and from older runners). `learnFacts` keeps it as `TargetFacts.appEnvironment` (persisted in `facts.json`). `AppEnvironmentNotice.decide` (target × marking × reported name × dismissed kinds) gives `reportsProduction` when the name is one of `AppEnvironment.productionNames` (`production`, `prod`, `prd`, `live`) and the target isn't marked production, or the informational `reportsLocal` when a production target's app says `local`, `development`, or `dev`; never for the sandbox. `AppEnvironmentBanner` shows it above the tab. Mark as Production calls `markAsProduction`, which saves the target through `saveProject`/`saveDockerProfile`/`saveSSHProfile` (so `targetEdited` revokes the grace); Dismiss adds the kind to `TargetFacts.dismissedEnvironmentNotices`. Nothing changes a marking automatically or runs code.
- **Saved connections' own marking ([#139](https://github.com/filipac/runlet/issues/139)).** `TargetLibrary.marking(for:connection:)` gives the stricter of the target's environment and the saved connection's (`TargetEnvironment.stricter`, by `strictness`), `fromConnection` when the connection's is stricter, and the connection's colour (else the target's). `guardProduction(…, savedConnection:)` decides with it for `.sql` and `.sqlSchema`, and `ProductionConfirmation.markedConnection` makes the sheet say the connection is marked as production and show it with its badge (and `ReadOnlyBadge`). `wantsSQLSchema`, the schema explorer's hint, the SQL bar (`SavedConnectionBadges`), and the run's history entry use the same marking. Test Connection doesn't ask (#138's choice).
- **History snapshot.** `startRun` reads the target's environment and colour when the run starts (for a saved connection, `marking(for:connection:)`); with the reported environment they go into the run's `HistoryEntry` (`targetEnvironment`, `targetColor`, `appEnvironment`, all optional, so older history decodes with nil). The History row draws the badge and colour from the entry, never from the target's current settings.

## SQL tabs (#35)

The user guide is [sql-tabs.md](sql-tabs.md); the driver API is in [drivers.md](drivers.md#sql-connections).

- **Model.** `TabLanguage` (`php`, `sql`) lives on `TabModel` and in `TabState`, `WorkspaceTab`, and `HistoryEntry`, with a tab's `sqlConnection` name (or, #138, `sqlSavedConnection` id and `sqlSavedConnectionName`; workspaces keep only the name); missing or unknown values decode as PHP. `AppModel.setLanguage(_:for:)` switches a tab (no language server for SQL, auto-run off); `.sql` files open as SQL tabs (`TabLanguage.forFile`).
- **Editor.** `EditorController.syntax` picks `SQLHighlighter` (from `SQLScript.tokenize` in RunletCore) or `PHPHighlighter`, and `CodeTextView.lineCommentMarker` is `--`. `bindLanguage` unbinds PHPantom for SQL tabs.
- **Scope and safety.** `SQLScript.statementToRun` picks the selection (one statement) or the statement at the caret and refuses several; `SQLScript.effect` classifies writes (best-effort). `AppModel.runSQL` asks `guardProduction(.sql, …)`, which always asks on production (`ProductionGrace` never skips `.sql`) and shows the statement and the write warning. `run(automatically:)`, the auto-run scheduler, and `startRun` refuse SQL tabs except through `runSQL`; MCP never reuses an SQL tab.
- **Running.** `SQLTabRun.code` generates `return \RunletRunner\SqlTab::run("<sql>", <connection|null>, <maxRows>);` with Explain's string escaping, and `startRun(…, sql:)` runs it like any snippet (snapshot, `ExecutionEngine`, every target kind), without strict types or magic comments. In the runner, `SqlTab::run` asks the booted driver's `sqlConnection()` (through `Runner::callBootedDriver`, so a project driver's errors name its file), then an Eloquent resolver or `$wpdb`, else throws `SqlUnavailable`. A PDO is prepared natively (MySQL: emulation and buffering off for the run, restored after); a callable returns rows or an affected count. The result is one `sql` event (`SQLResultInfo`: columns, rows of `SQLCell`, `affectedRows`, truncation, timing, driver, source, connection names), bounded to 1,000 rows (from the app), 200 columns, 8 KiB per cell, and 8 MiB per result.
- **Output.** `OutputItem.sql` renders `SQLResultCard` (the result's `ValueTable` in the shared table view, or the affected rows). `SQLResultInfo.table` is stored, not computed: built in `init(from:)`, where `RunSession` decodes the `sql` event on the pump's task, and again only when `columns` or `rows` change; it isn't encoded. `ValueTableView` keeps its search and sort in view state and computes the shown rows with `ValueTableQuery` on a detached task when they change (`.task(id:)`, typing debounced); `ValueTableGrid` (an `NSViewRepresentable` over `NSTableView`) reloads only when the rows or columns change. Its height comes from `OutputTableLayout` (RunletCore: up to 400 points), and its scroll view hands a vertical gesture it can't take to the output (`OutputTableLayout.scrollGoesToOutput`). The card's copy text is made on Copy (`Card.copyTextProvider`). While an SQL run is active, `SQLRunningRow` shows `TabModel.sqlActivity` ("on the default connection", "3 statements on …"), the elapsed time since `RunState.running`, and Stop, in all three display modes ([#162](https://github.com/filipac/runlet/issues/162)). An SQL run's empty `result` is not shown, and its errors lose the runner's and generated snippet's locations. History records the statement with `language: sql`. Connection names reported by a run fill the tab bar's picker for that target (`SQLConnectionCatalog`, session only).
- **Run All Statements (#129).** `SQLScript.statementsToRunAll` takes the selection's statements (or the tab's); `AppModel.runAllSQL` refuses scripts with their own transaction statements (`SQLScript.transactionControl`) while the tab's `sqlTransaction` (in `TabState`, nil = on) is set, asks `guardProduction(.sql, …, sqlStatements:)` (the sheet lists each statement with its `SQLScript.effect` warning), and runs `SQLTabRun.scriptCode`: `SqlTab::runAll([['sql' => …, 'line' => …, 'implicitCommit' => …], …], <connection>, <maxRows>, <transaction>)`. The runner resolves the connection once, emits one `sql` event per statement with `statement {index, count, line, text}`, stops at the first error with `SqlStatementFailed` (which names the statement and says what was rolled back and what didn't run), and commits at the end. `implicitCommit` (`SQLScript.commitsImplicitly`) matters on MySQL and Oracle only: a notice before the first statement, and a new transaction after each such statement. `SQLRunInfo` carries the statements, the transaction flag, and the history text.
- **Bound parameters (#145) and the parameters drawer (#168).** `SQLParameters.scan` (RunletCore, `SQLParameters.swift`) reads the run's statements with `SQLScript.tokenize` (with the saved connection's or the schema's driver when known: MySQL's backslash escapes, PostgreSQL's `#`; `#` is a comment only for MySQL, SQLite, and an unknown driver, not for SQL Server's `#temp` tables or a custom DSN) into an `SQLParameterScan`: one `SQLParameter` per `:name` (shared by every statement of a Run All) and per `?` of each statement (`.positional(statement:index:)`), each statement's keys in binding order, per-statement name counts, and the first `SQLParameterProblem` (mixed kinds, `$1`, a name PDO reads differently), which `runSQL`/`runAllSQL` show as an alert before anything else. `??` is skipped as PDO's escape. The values come from the tab's drawer: `SQLParameterDrawerModel` (RunletCore, `SQLParameterDrawer.swift`) turns the tab's text, selection, and driver into `Content` (rows, problem, `-- @param` problems, statement count) for its scope (`.statement`: `SQLScript.statementToRun`; `.all`: `statementsToRunAll`), skipping the work when nothing changed. Each `SQLParameterRow` comes from `SQLParameterRows.make`: the tab's `SQLParameterMemory` (`SQLParameterDraft`s, i.e. type, text, and flag, set in the drawer, keyed `:name` or `?N` plus the statement's trimmed text), else `SQLParameters.presets` (`-- @param` comments), else not set. On an edit, a statement at the same place in a tab with as many statements carries its `?` drafts to its new text and a `:name` renamed in place to its new name. In the app, `SQLParameterDrawer` (`AppModel+SQLParameters.swift`, `@Observable`, one per tab in `SQLParameterStore`, in memory only) holds the model and republishes `content` only when it changed; `TabModel.onChange` (edits and caret moves of SQL tabs) schedules `refreshSQLParameters` after 150 ms plus three times the last update's duration, so typing stays smooth. `SQLParameterDrawerView` (`Features/`) sits under the `CodeEditorView` in SQL tabs only, with layout priority so a short pane shrinks its list (fixed 28 pt rows in a `LazyVStack`, at most 5.5 visible) rather than the editor. `withSQLParameterValues` (used by `runSQL`, `runAllSQL`, and `explainSQL`) refreshes the drawer at once (so an edit just before the run has carried its values), reads `SQLParameterDrawerModel.rows(for:statements:text:)` for the run's own scan, and either calls the continuation with the values or switches the drawer's scope, sets its note, and focuses the first missing or invalid row (`SQLParameterDrawer.focusRequest`); nothing runs. The continuation builds `[[SQLBinding]]` (`SQLParameterScan.bindings`), sets `SQLRunInfo.values` (the output's note) and `historyCode` (`SQLParameters.historyCode`: `-- @param` lines before the text, `?` lines before their statement), then asks `guardProduction(…, sqlValues:)` and runs `SQLTabRun.code(…, bindings:)` / `scriptCode(…, bindings:)`. The values travel as PHP literals in an array argument (`[['name' => 'id', 'type' => 'int', 'value' => 42, 'uses' => 2], ['position' => 1, …]]`; a Run All statement's `params`), inside the request on stdin; never in the SQL text. In the runner, `SqlTab::refuseUnbindable` throws `SqlParametersRefused` after resolving the connection and before anything runs, for a callable connection with values or, on MySQL, a name used more than once in a statement (`uses`); `runPdo` turns emulated prepares off when there are values, then `SqlTab::bind` calls `bindValue` with `PARAM_STR` (text and decimals), `PARAM_INT`, `PARAM_BOOL`, or `PARAM_NULL`. Write as @param Comments: `SQLParameterDrawerModel.writingDeclarations()` (`SQLParameters.writingDeclarations`) rewrites a placeholder's own `--` `@param` line or inserts lines before the statement that uses it, and `EditorController.replaceChangedPart(with:actionName:)` applies the difference as one named undo group (`FormattingEdit`, as Format Code does). `SQLScript.statements(in:)` counts statement lines on from the previous statement (`LineCounter`), so splitting stays linear in the text's length.
- **Explain Statement (#147).** `AppModel.explainSQL(_:mode:)` (`AppModel+SQLExplain.swift`) takes the statement like Run, refuses EXPLAIN/DESCRIBE/ANALYZE statements, and, for Explain Analyze, refuses what the known driver (a saved connection's, or the schema's) or a read-only connection would refuse; placeholders take their values from the parameters drawer (`withSQLParameterValues`, #168). It then asks `guardProduction(.sqlExplain(analyze:), …)` on production (with `SQLExplain.productionWarning`), or, off production, `SQLExplainUI.pendingAnalyze` (an alert on the tab's window, Cancel the default) before Explain Analyze of a write, and starts the run with `SQLRunInfo.explain` set (the note, the running label, and Run History's first line say what it does). `SqlTab::explain()` resolves the connection as `run()` does, refuses unbindable values, and hands it to `SqlExplain::explain()`, which picks the dialect from the PDO driver (MariaDB from the server version; `$wpdb` is MySQL; SQL Server and callables are refused), prefixes the dialect's EXPLAIN, prepares it natively (a second statement is refused, never run), binds the values through `SqlTab::bind()`, and emits an `sqlPlan` event with the raw JSON or text (at most 4 MiB) or SQLite's rows. Explain Analyze refuses SQLite, and writes on MySQL/MariaDB (`SqlReadOnly::refusal` as the write check) and on read-only connections before connecting; on PostgreSQL it runs inside `beginTransaction()`/`rollBack()`. `RunSession` decodes the event into `RunEvent.Kind.sqlPlan`; `OutputItem.sqlPlan` renders `SQLPlanCard` (`SQLPlanViews.swift`): a tree of at most 300 visible rows with collapsible steps, full-scan highlights, estimate and actual columns, and a Raw toggle.

The user guide is [mcp.md](mcp.md).

- **Processes.** An AI client starts `Runlet.app/Contents/Helpers/runlet mcp` and talks MCP to it over stdio. The tool answers the protocol itself (`MCPServer`) and sends each tool call over a Unix socket to the running app (`MCPAppClient` → `MCPSocketListener`). It starts Runlet in the background when nothing listens; starting never runs code. The app listens only while Settings ▸ AI Clients is on (`AppSettings.mcpServerEnabled`, off by default).
- **Approvals.** Every `run_php` goes through `MCPApprovalPolicy` in the app. Only a sandbox run on a connection whose user ticked "Allow for this session" runs without the sheet. The approval and the allowance belong to the app's connection object, never to message fields. The sheet doubles as the production confirmation: `guardProduction` and `ProductionGrace` aren't consulted for MCP runs, so the grace never skips one and approving one never grants it.
- **Runs.** An approved run uses the same `startRun` path as the Run button (snapshot, `ExecutionEngine`, history), in a tab named after the client, with a note in the output saying who asked. A `RunObserver` streams events into `MCPRunReport`, which answers the call when the run ends.
- **Never on its own.** Listing, reading, and saving snippets run nothing; a waiting request is withdrawn when the client cancels or disconnects, when it expires, or when the server is turned off; an SSH profile's state is read from its local control socket only.

## SSH targets

The full user guide is [ssh.md](ssh.md); the design is in [done-next-release-ideas.md §3](done-next-release-ideas.md#3-ssh-targets--design-proposal).

- **Client.** The system `/usr/bin/ssh`, never a library and never `-F` (Debug builds' `RUNLET_SSH_CONFIG` aside), so `~/.ssh/config` (`Include`, `Match`, `ProxyJump`), agents including 1Password's, `known_hosts`, and `UseKeychain` behave as in the user's terminal. Runlet stores no keys or passwords and handles no secret.
- **Runs.** `ssh -T -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o LogLevel=ERROR -o RemoteCommand=none -o PermitLocalCommand=no -o ClearAllForwardings=yes -S <socket> -o ControlMaster=auto|no [-C] [-l] [-p] [-J] -- <host> "/bin/sh -c '<script>'"`. The script enters the directory (printing a marker when it can't), exports `RUNLET_RUN_ID`, and `exec`s PHP with the usual `-d` arguments, so PHP leads the SSH session's process group. The runner arrives on stdin; nothing is written on the server except, with `SSHProfile.keepCompiledPHP` (on for new profiles, off for profiles saved without the key), PHP's opcode file cache in `~/.cache/runlet/opcache` (0700; not with a container step).
- **Shared connection.** Every call for a profile uses one OpenSSH control socket. Automatic (agent or key) profiles use `ControlMaster=auto` with `ControlPersist=<minutes>m` (or `yes`); interactive (password/2FA) profiles use `ControlMaster=no`, and `AppModel.sshSnapshot` refuses to run until Connect… has opened the socket.
- **Failures.** `PreparedLaunch.explainFailure` maps `ssh` exit 255 and its message (unknown or changed host key, rejected keys, unresolvable host, timeouts, refused connections, a lost connection), the missing-directory marker, and exit 127 to plain language through `SSHFailure`.
- **Status.** `SSHControlSocket` connects to the socket on this Mac and closes it at once: connected, disconnected (no file), or expired (a stale file). Checking never starts `ssh`, so it never reads `~/.ssh/config` or reaches the network. Tabs check when they appear and when Runlet becomes active; runs, Connect…, and Disconnect check afterwards.
- **Connect… (password, keyboard-interactive, 2FA, unknown host keys).** `AppModel.connectSSH` removes a stale socket and opens a terminal tab (`TerminalRequest.executable`, not a command tab) running `ssh -M -S <socket> -o ControlPersist=yes -o BatchMode=no -o StrictHostKeyChecking=ask … -N -f <host>`. OpenSSH prompts in the pty; Runlet never reads the input. After authentication `-f` daemonizes the master (detached from the pty, stdio on `/dev/null`) and the tab's process exits 0, so the tab closes; `AppModel+Terminal`'s exit hook calls `sshTerminalExited`, which re-reads the status. The master outlives Runlet: a restart finds it through the socket. Disconnect is `ssh -O exit`, after asking when runs on that profile are in progress. `SSHRunTests.connectLogsInThroughAPseudoTerminalAndDisconnectEndsIt` drives the same argv through `script(1)` against the fixture's password account.
- **Local folder.** `TargetLibrary.localFolder(for:)` gives an SSH profile's checkout on this Mac to the same places a Docker profile's local source goes: the language workspace (else the basic workspace), `projectRoot` (project snippets), `hostDirectory` (host commands), `projectFolder` (Open in Editor), the terminal's start folder, and static facts. `EditorPathMapping.remote(roots:localRoot:host:)` maps server paths under the profile's directory and the run's reported working directory (its real path), and a root ending in `/current` also covers every `releases/<id>/` beside it.
- **Commands and shells (SSH-5).** `ProjectCommandLauncher` runs a listed command as `ssh -t` (purpose `.terminal`: a pty, otherwise the batch options) with `/bin/sh -lc 'cd <dir> || explain; <command>'`, so `~/.profile` adds to PATH as in a login; commands that need input open `exec "$SHELL" -l` in the directory and type the command without Return. `AppModel.openSSHShell` (terminal "+", target menu, Commands panel, palette) resolves like a run and opens the same login shell. Production hosts ask before every command, listing, and shell (`GuardedAction.shell`); the snippet grace never covers them. Open REPL uses the same `ssh -t` path with `ProjectREPL.selectionScript` (the server picks Tinker, PsySH, or `php -a`), asks every time on production (`GuardedAction.repl`), and connects only on that click, under the same rules (a password host must be connected first). The Tests group (#40) uses the same path with `ProjectTests.selectionScript` (the server picks `php artisan test`, Pest, or PHPUnit, and explains when there is none) and is disabled on production hosts. `SSHRunTests` runs these argvs under `script(1)` against the fixture.
- **Docker on the host (SSH-6).** `SSHProfile.container` (`RemoteContainerStep`: Compose identity or name, working directory, PHP, user, TMPDIR, Docker command) makes `AppModel.sshSnapshot` list the server's containers through a `DockerCLI` with the SSH transport and resolve them with `DockerProfileResolver` (ambiguity or a replaced name-only container opens `ContainerChoiceSheet` via a target-agnostic `ContainerChoice`; a chosen replica stays chosen while it runs). The snapshot is `.ssh` with the Docker fields set plus `dockerCommand` and `localFolderRoot` (the container path of the server directory's bind mount), and `ExecutionEngine` sends it through `DockerExecAdapter` with the remote `DockerCLI` (re-check before launch, `docker exec -i`, runner-only Stop). `EditorPathMapping.forSnapshot` maps container paths through `localFolderRoot` (else the container directory and the run's real directory). Recording the resolved container ID is not an edit (no revision bump; a production grace stays). Test Connection adds a `RemoteContainerCheck` (resolution plus `ContainerProbe`); a host without PHP is reported as fine. Tests use `Tests/Fixtures/docker/ssh/fake-docker` on the SSH fixture.
- **Never on its own.** Opening, restoring, or switching to an SSH tab, and launching Runlet, never connect. Facts come from the local folder; the server's PHP version from runs and Test Connection. The Commands panel lists an SSH host's commands only when asked.

## Laravel sandbox

- **Template.** `Resources/Sandbox/laravel` holds Laravel 13.34.0, which requires PHP `^8.3`. `scripts/build-sandbox.sh` installs its locked dependencies and builds a pre-migrated SQLite database on the build machine. `runlet-sandbox.json` records `laravelVersion`, `phpConstraint`, `minimumPHP` (8.3), and `dockerImage` (`php:8.4-cli`).
- **Install.** `SandboxManager.ensureInstalled()` copies the immutable template from the bundle into `Sandbox/laravel-<version>/` under Application Support, using a staging directory `.install-<uuid>`. It then:
  - writes a `.env` with a random `APP_KEY`, SQLite, array sessions, a file cache, a sync queue, and the `log` mailer
  - creates the storage directories
  - writes a `.runlet-installed` marker

  `reset()` deletes only that directory and reinstalls it.
- **Runtime choice.** `chooseRuntime` follows the sandbox runtime preference in Settings (`automatic`, `localPHP`, or `docker`). Unless the preference is `docker`, it picks the first match from this list:
  1. The preferred PHP, if it is version 8.3 or newer and has the tokenizer.
  2. Otherwise, the first compatible discovered PHP (`PHPDiscovery.preferred`: discovery order, so the `php` on `PATH` comes first; stable releases before prereleases). Runlet's own PHP, when downloaded, is last in that list ([#2](https://github.com/filipac/runlet/issues/2)).
  3. Otherwise, with the `localPHP` preference, `unavailable`.

  Then (or directly with the `docker` preference) it uses Docker if the CLI exists and its engine responds. `imagePresent: false` means the first use needs an image download, which the app offers as **Download Docker Image**. Otherwise the result is `unavailable`, with an explanation.

  The Docker sandbox mounts the installed copy at `/sandbox`.

## Persistence

`AppPaths.standard` is `~/Library/Application Support/Runlet`. If `RUNLET_DATA_DIR` is set and not empty, Runlet uses that directory instead.

```text
<root>/
  State/
    settings.json                 AppSettings
    targets.json                  TargetLibrary (local projects, Docker profiles, SSH profiles,
                                  saved database connections' definitions; never passwords)
    snippets.json                 personal snippets (optional description; legacy entries omit it)
    history.json                  execution history (SQL runs with their connection's name, #149)
    session.json                  SessionState (tabs, selected tab)
    <name>.last-good.json         previous valid copy
    <name>.corrupt-<timestamp>.json   preserved unreadable file
  Sandbox/laravel-<version>/      writable sandbox install (see above)
  LanguageService/
    config-<hash>/phpantom_lsp/.phpantom.toml   per-workspace PHPantom global config
    basic-workspace/              root for workspaces without local source
  ShellIntegration/               zsh/.zshenv … .zlogin and bash/runlet.bash for command tabs (rewritten on use)
  SSH/                            OpenSSH control sockets, <first 8 hex of the profile id>.sock (0700)
  LocalConnections/               empty working folder of saved connections opened from this Mac (#142; 0700), through SSH tunnels too (#143)
  Runs/                           declared in AppPaths; unused (the runner writes no files)
  Logs/                           declared in AppPaths; unused by package code
```

Saved database connections' passwords ([#138](https://github.com/filipac/runlet/issues/138)) are not in this folder: they are generic passwords in the login keychain (service `dev.runlet.Runlet.database`, account = the connection's id, not synchronizable). A data folder other than the standard one uses the service `dev.runlet.Runlet.database.<8 hex of a hash of its path>`, and Debug builds with a scratch `RUNLET_DATA_DIR` keep them in memory instead.

How `JSONDocumentStore` works:

- **Envelope.** Each file is `{ "schemaVersion": 1, "savedAt": …, "data": … }`.
- **Save.** If the current file still decodes, it is first copied to `<name>.last-good.json`. The new data is written to a temporary file in the same directory and moved into place with `rename()`.
- **Load when missing.** If the file is missing, the last-good copy is used, or the default value if there is none.
- **Load when unreadable.** A file that cannot be decoded, or that has a `schemaVersion` newer than this build supports, is moved aside to `<name>.corrupt-<ISO 8601 timestamp>.json`. The last-good copy is restored if it decodes; otherwise the default is used.
- **Recovery notes.** Loading returns recovery notes for display.
- **Settings.** `AppSettings` decoding fills missing keys with defaults.

The app layer adds the rest. `AppModel` debounces session and history writes by 0.5 s, saves the session when the app resigns active, and flushes both on quit. Settings, targets, and snippets are saved on every change. History is trimmed to `AppSettings.historyLimit` (default 1000, adjustable in Settings). Restoring a session, history entry, or snippet loads code only. Sandbox tabs can explicitly opt into [auto-run](sandbox-auto-run.md) for subsequent editor edits: `TabModel` keeps the unsaved opt-in and cancellable 800 ms task; `EditorController` distinguishes edit events from code loads; `AppModel.run` rechecks sandbox ownership and runs the whole tab. Code loads and target changes disarm auto-run, while Stop/explicit Run/close cancel pending evaluation. Sessions and workspaces omit the opt-in.

## Terminal

The terminal panel runs the user's own login shell, untouched, for plain tabs. A tab that types a command (`TerminalRequest.commandLine`, e.g. a project command run locally) must not type it before the shell is ready: an rc file may ask a question first (oh-my-zsh's dotenv plugin, `read -q`, an oh-my-zsh update prompt), and the command's first character would answer it.

- **Readiness marker.** For zsh, bash, and fish, the shell writes `ESC ] 6973 ; RunletReady ; <token> BEL` once, just before its first prompt, after every startup file ran. The token is random per tab. `TerminalSession` feeds output to `ShellIntegration.ReadyScanner` (a marker split across reads is still found) and registers a no-op SwiftTerm OSC 6973 handler, so the sequence is never drawn. After the marker, it waits until the line editor puts the pty in raw mode (at most 1 s) and types the command; typed earlier, the tty would echo it above the prompt. A command is never typed into a shell that has not reported; after 15 s the panel shows Run Now / Don't Run instead. A marker that comes later (the user answered the question) still types the command.
- **zsh.** `ZDOTDIR` points at `ShellIntegration/zsh` (`RUNLET_USER_ZDOTDIR` carries an inherited `ZDOTDIR`, `RUNLET_SHELL_READY_TOKEN` the token; both are unset before any user file runs). Each of Runlet's files puts the user's `ZDOTDIR` back (value, export flag, or unset), sources the user's file of the same name from it, records any change the file made, and points `ZDOTDIR` back at Runlet's directory for zsh's next startup file. So a `ZDOTDIR` set in `~/.zshenv` is followed, and `/etc/z*` files still run in order. `.zshrc` resets `HISTFILE` when `/etc/zshrc` derived it from Runlet's directory. `.zlogin` (or the first file after which zsh reads no more, e.g. `NO_RCS`) leaves the user's `ZDOTDIR` in place, removes every helper function and variable, and adds a one-shot `precmd` hook that writes the marker to `/dev/tty` and removes itself. precmd first runs after all startup files, so a question in any of them holds it back. Nothing prints during startup (Powerlevel10k's instant prompt warns about console output).
- **bash.** `bash --rcfile ShellIntegration/bash/runlet.bash -i` (non-login, because `--rcfile` is ignored for login shells). The rc file reads what `bash -l` reads (`/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`) and appends a one-shot `PROMPT_COMMAND` entry (string, or array on bash 5.1+) that removes itself wherever other hooks moved it. Differences from a real login shell, in command tabs only: `shopt login_shell` is off, `$0` is `bash`, `logout` refuses, and `~/.bash_logout` is not read.
- **fish.** `--init-command` (runs after `config.fish`) defines a `fish_prompt` handler that writes the marker and erases itself; fish stays a login shell.
- **Fallback.** Other shells (sh, tcsh, nu, …), direct executables with a command line, and zsh/bash when the scripts cannot be written use output heuristics: type once the line editor announced itself (bracketed paste `ESC[?2004h` or keypad mode `ESC[?1h` while the pty is raw) and output settled for 0.3 s, or, for shells that never announce it, after 3 s of quiet (1.5 s for direct executables). zsh and fish are never typed into blindly; the 15 s notice applies.
- **Command tabs.** A tab with `isCommand` (every project command, including `docker exec … sh -lc <cmd>`) stays open when its process exits, with the exit line, a check or warning mark in the tab strip, and Run Again / Close in the notice bar; Return, ⌘W, or × closes it. Plain and container shells that exit with 0 close as before.

## Language service (PHPantom)

- **Binary.** `Resources/LSP/phpantom_lsp` is a universal binary. It is copied to `Contents/Helpers/phpantom_lsp` in the app bundle.
- **Launch.** PHPantom runs with `--stdio`, with the workspace root as its working directory. Its environment is minimal: `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `LANG`, `LC_ALL`, and `PATH=/usr/bin:/bin`, which has no host PHP. `XDG_CONFIG_HOME` points to an app-owned config home.
- **One process per workspace.** `LanguageService` keeps one `LanguageServerSession` per `LanguageWorkspace`, keyed by kind (`project` or `basic`), root path, and optional PHP version. Tabs acquire and release a session by tab ID, and the server stops when the last tab releases it. Workspaces with different keys never share a process.
- **App-owned global config.** `PHPantomConfig` writes `LanguageService/config-<FNV-1a of kind|root|phpVersion>/phpantom_lsp/.phpantom.toml`. PHPantom reads it as its global config. It sets:
  - an optional `[php] version`
  - `[diagnostics] workspace = false`, `workspace-external = false`
  - `[formatting] pint`, `php-cs-fixer`, `phpcbf = ""`
  - `[phpstan]`, `[phpcs]`, `[mago] command = ""`

  The user's own global PHPantom config is never modified, because PHPantom looks for its global config under `XDG_CONFIG_HOME`. A project's `.phpantom.toml` is read but never modified. It merges on top, so a project that sets a tool command explicitly opts back in.
- **Scratch documents.** Each tab's URI is `file://<root>/.runlet-scratch/tab-<uuid>.php`. PHPantom resolves it against the real project root, and the file is never created on disk. Every change sends the full text with an increasing version number.
- **Model copies.** On every start of a `project` session, `EloquentOverlay` reads the PHP files under the project's Composer `autoload.psr-4` directories (or `app/`) and opens adjusted in-memory copies under the files' own URIs (`textDocument/didOpen`) for two shapes PHPantom 0.10.0 misreads: a relation method with only a native relation return type (the type is blanked to spaces, so PHPantom infers the related model from `$this->hasMany(X::class)`), and a `casts()` array without a trailing comma (a comma is added). Nothing is written; the copies are rebuilt on restart, and `LanguageServerSession(modelOverlays: false)` turns them off. Details, limits, and the upstream report drafts are in [compatibility.md](compatibility.md#runlets-model-copies) ([#55](https://github.com/filipac/runlet/issues/55), retirement tracked in [#117](https://github.com/filipac/runlet/issues/117)).
- **Runlet's snippet API.** On every start of any session, `RunletAPIStub` opens declarations of the `Runlet\` functions and `Runlet\Inspector`'s public methods as an in-memory document (`<root>/.runlet-scratch/runlet-api.php`, never written), so `\Runlet\` completes and hovers in snippets ([#196](https://github.com/filipac/runlet/issues/196)). `RunletAPIStubTests` compares its signatures with the built runner's by reflection.
- **Line mapping.** If the editor text has no opening tag, `ScratchDocumentMapping` adds `<?php\n` as its own line. Editor line *n* maps to LSP line *n*+1, and columns do not change. Positions inside the synthetic line clamp to (0, 0), so import `additionalTextEdits` land on editor line 0. Both sides use UTF-16 positions, and the client advertises `positionEncodings: ["utf-16"]`.
- **Snippet syntax.** `SnippetText` converts PHPantom's snippet syntax to plain text plus a cursor offset. PHPantom 0.10.0 sends snippet syntax even though the client declares `snippetSupport: false`. For calls (methods, functions, classes after `new`), `CompletionInsertion` drops placeholder text and inserts `name()`: the caret goes inside when the callable takes parameters (a tab stop, or a non-empty parameter list in the label) and after `)` when it takes none. Built-in functions and classes come without a parameter list, so the caret starts inside and the editor steps past `)` if signature help reports no parameters. If `(` already follows the word, only the name is inserted.
- **Features used.** Completion with resolve, hover, signature help, and pushed diagnostics (`publishDiagnostics` with version support).
- **Crash restart.** After an unexpected exit, the session restarts with a backoff of 300 ms × attempt, up to 5 attempts. It reopens documents from the client's copy of their text. State is reported as `stopped`, `starting`, `ready`, `restarting`, or `failed`. A manual restart resets the attempt counter.
- **No local source.** Docker profiles without a mapped checkout use a `basic` workspace (`LanguageService/basic-workspace`) for core PHP completion. `LanguageWorkspace.sourceLimitations()` describes what is missing: an unmapped source, a missing directory, or a missing `vendor/`.

- **App icon** (`ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`): `Runlet/AppIcon.icon`, an Icon Composer icon (Liquid Glass, with default, dark, tinted, and clear styles), and a classic `Runlet/Assets.xcassets/AppIcon.appiconset` (16–512 pt, @1x and @2x). 4. Runs the packaged self-test, `Runlet --self-test` (with `--docker` when `RUNLET_SELFTEST_DOCKER` is set), against a temporary `RUNLET_DATA_DIR`, and writes the report to `dist/self-test.json`.
5. Creates `dist/Runlet.zip` (`ditto`) and `dist/Runlet.dmg` (`hdiutil`, UDZO).

Signing is ad-hoc by default (`RUNLET_SIGN_IDENTITY` defaults to `-`). With a Developer ID identity in `RUNLET_SIGN_IDENTITY` and a `notarytool` keychain profile in `RUNLET_NOTARY_PROFILE`, the script also submits the DMG for notarization and staples it.

**Tracked in [#24](https://github.com/filipac/runlet/issues/24):** Developer ID signing and notarization have not been run. They need a Developer ID Application identity and a `notarytool` keychain profile. Until then, builds are ad-hoc signed: they run on the build machine (natively and under Rosetta, see [validation.md](validation.md)), but Gatekeeper is expected to block a downloaded copy on other Macs.
